# Focused Stage 2 Auth Review

Reviewed locally on 2026-10-21; source inspection only. No cloud/auth UAT or tests were run while the IDE was writing.

## Findings

1. **P1 — Router recreation and lifecycle leak confirmed.** `appRouterProvider` watches the entire auth state and returns a new `GoRouter` for every state change (`app_router.dart:31-34`); each uses the same `_rootNavigatorKey`, `initialLocation: /splash`, and no `ref.onDispose(router.dispose)`. Repro: navigate into a nested branch, trigger `signIn` (`authenticated → loading → authenticated`) or any auth error; the root receives replacement router instances, risking reset history, duplicate-key assertions during overlap, and leaked listeners. Keep one router and refresh/notify its redirect logic, or dispose replacements explicitly without reusing a live key.
2. **P1 security gate — `loading` fails open.** Redirect handles initial, unauthenticated/unconfigured/error, onboarding, and authenticated; `AuthStatus.loading` falls through `null` (`app_router.dart:57-88`). A protected or `/admin` location evaluated while restore/sign-in/onboarding is pending is admitted by the client guard. Deterministic repro: evaluate redirect for `AuthState(status: loading)` at `/admin` or `/practice/text`; result is `null`. Loading must route to/stay on a non-sensitive gate until identity and role resolve. Backend authorization remains mandatory.
3. **P0 — Admin role trusts user-editable metadata.** Supabase login/restore sets `_isAdmin` when either `appMetadata.role` **or `userMetadata.role`** is `admin` (`auth_repository.dart:256,294`). User metadata must not grant privilege. Remove that branch; derive authorization from server-controlled claims and require backend role enforcement for every admin API. The UI guard is defense in depth only.
4. **P0 — Logout/account change does not perform scoped cleanup.** `AuthController.signOut` only awaits repository sign-out and overwrites auth state (`auth_controller.dart:169-172`). It does not call `ApiClient.cancelSession`, invalidate account-scoped Riverpod caches, or stop/dispose recording/playback/realtime resources. A late response or cached provider can cross the account boundary. Centralize account-transition cleanup before clearing identity and test pending requests/media plus A→logout→B cache isolation.
5. **P1 — Supabase auth events are not observed.** No `onAuthStateChange` subscription handles `tokenRefreshed`, remote/local `signedOut`, user deletion, refresh failure, or stream errors. `getAccessToken` merely reads the current session and suppresses errors. A revoked/deleted session can leave UI auth state stale until an API 401 or restart. Subscribe once, cancel on disposal, and drive the controller through explicit event states without refresh loops.
6. **P1 — Initialization failure is silently converted into signed-out behavior.** `main.dart:14-22` swallows `Supabase.initialize` failure. `restoreSession` then catches all SDK errors and returns null (`auth_repository.dart:245-271`), so valid-looking production configuration can show Welcome instead of an unavailable/configuration state. Preserve a sanitized initialization failure and fail closed visibly.
7. **Positive boundary:** production defaults to `SupabaseAuthRepository`; `LocalAuthRepository` is selected only by explicit `DEMO_MODE=true` (`auth_controller.dart:10-16`). Keep a persistent, prominent demo label and release/config check so demo mode cannot silently ship as production.

Required local regression tests: router identity/history across auth transitions; loading denial for every protected/admin deep link; user metadata cannot grant admin; one server-controlled admin success; auth-event refresh/sign-out/deletion/error; logout cancels pending API/media and invalidates user caches; Supabase initialization failure becomes unconfigured; production mode never selects local auth. Real Supabase/JWT/backend IDOR and UAT-01/UAT-07 remain pending.
